# Agent Workspace Guide

This repository root is an orchestration workspace, not a single application.

## Directory Map

- `frontend/` - Next.js frontend cloned from `git@github.com:vedlct/Waste_Service.git`.
- `backend/` - Laravel backend intended for the admin panel, CMS, and API.
- `docs/` - project requirements, API notes, admin-panel decisions, deployment notes, and other long-lived context.

## Frontend Notes

- Work from `frontend/` for frontend tasks.
- Key files and folders:
  - `frontend/package.json` - scripts and JavaScript dependencies.
  - `frontend/src/` - application source.
  - `frontend/public/` - static assets.
  - `frontend/AGENTS.md` - Next.js-specific agent instructions generated by the frontend project.
- Common commands:
  - `npm install`
  - `npm run dev`
  - `npm run build`
  - `npm run lint`
  - `npm test` (Node's built-in runner over `frontend/tests/**/*.test.mjs`; no extra dependencies)
- Files under `frontend/src/lib/` that tests import must use relative imports, not the `@/` alias, because Node's test runner does not resolve it.
- The frontend reads from and submits to the backend's `/api/v1` API through `frontend/src/lib/api.js`. Copy `frontend/.env.example` to `frontend/.env.local` and set `NEXT_PUBLIC_API_URL` to the backend base URL. It is inlined at build time, so rebuild after changing it.
- Every page that reads from the API keeps a hardcoded fallback, so the frontend builds and renders with the backend stopped.
- The API contract is `docs/api.md`.

## Backend Notes

- Work from `backend/` for Laravel/admin/API tasks.
- Before starting backend/admin/API work, read `docs/BACKEND_PLAN.md`.
- Keep `docs/BACKEND_PLAN.md` updated after every backend/admin/API change so the team can track completed work, active decisions, and next steps through the end of the project.
- Key files and folders:
  - `backend/composer.json` - PHP dependencies and Laravel scripts.
  - `backend/app/` - application code.
  - `backend/routes/` - web and API route definitions.
  - `backend/database/` - migrations, factories, seeders, and local SQLite file if used.
  - `backend/config/` - framework and app configuration.
- Common commands:
  - `php8.4 /usr/local/bin/composer install`
  - `php8.4 artisan serve`
  - `php8.4 artisan test`
  - `php8.4 artisan migrate`
  - `npm install`
  - `npm run dev`

## Environment Notes

- The backend was installed with `php8.4 /usr/local/bin/composer create-project laravel/laravel backend`.
- The backend is Laravel 13. `composer.lock` pins Symfony 8.1, which requires PHP >= 8.4.1, so PHP 8.4 is the real minimum.
- On this Windows/Laragon machine, PHP 8.4.25 lives at `G:/laragon/bin/php/php-8.4.25-Win32-vs17-x64/php.exe`. The default CLI `php` is still 8.3.16 and cannot run the backend, so call the 8.4 binary explicitly:
  - `G:/laragon/bin/php/php-8.4.25-Win32-vs17-x64/php.exe artisan test`
  - `G:/laragon/bin/php/php-8.4.25-Win32-vs17-x64/php.exe C:/ProgramData/ComposerSetup/bin/composer.phar install`
- Local database is MySQL `mr_tee` on Laragon's MySQL (root, no password). The legacy `mrtree` database on the same server is unrelated and must not be touched.
- Tests run against a separate `mr_tee_testing` database (set in `backend/phpunit.xml`) and are rolled back after each test. They must never be pointed at `mr_tee`; the base `TestCase` refuses to.
- Production deployment, the `.env` checklist, and backups are in `docs/deployment.md`. Never run `db:seed` against production once it has data.
- See `docs/BACKEND_PLAN.md` under Known Environment Notes for the full Laragon setup details.

## Docs Workflow

- Check `docs/README.md` first when looking for project context.
- For backend/admin/API work, check and maintain `docs/BACKEND_PLAN.md` in addition to the other long-lived docs.
- Put requirements and decisions in `docs/` instead of burying them in chat history.
- Update this root `AGENTS.md` when new top-level directories, services, or important workflows are added.

## Working From Root

- Do not assume root-level package commands exist.
- Choose `frontend/` or `backend/` first, then run commands from that directory.
- Avoid broad scans of `node_modules/`, `vendor/`, build outputs, and generated caches unless the task specifically requires them.
